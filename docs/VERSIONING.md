# 版本命名规范

> **一句话**：有没有「功能更新」决定动哪一位 —— **有功能更新进次版本（+0.1.0），
> 没有就进补丁版本（+0.0.1）**；本仓的版本号指的是**这套排障方法与工具的版本**，
> 只在 [CHANGELOG.md](../CHANGELOG.md) 的版本标题里维护。

适用范围：本仓的**仓库发布号** —— [CHANGELOG.md](../CHANGELOG.md) 的版本标题、
Release 说明文件名、发版 tag，三处**必须一致**。

本仓是**方法与工具**仓库，**没有构建产物**：三个工具
（`tools/clear-chrome-region.js` / `tools/verify-gemini.sh` / `tools/cdp.js`）
都是**直接跑的源码**，脚本里没有 `version` 字段；本仓也**没有** `package.json` /
`pyproject.toml` / `version.txt` 之类带版本号的清单文件。
**别去任何配置文件里找版本号** —— 版本号是**手工维护的发布号**。

**本仓的「版本」指的是什么**：这套**排障方法与工具**的版本 ——
判定方法变了、工具多了或行为变了，就是「功能更新」；
本仓**不发布任何产物**（没有 npm 包、没有安装包、没有镜像），
所以这个版本号只标注「这套方法与工具现在是什么样」。

---

## 1. 三段式与进位规则

版本号是三段式：`主版本.次版本.补丁版本`（如 `0.1.0`）。

| 这次发版包含…… | 动哪位 | 写法 | 例子 |
|---|---|---|---|
| **没有功能更新** —— 只修 bug、改措辞、补证据、改文档 | **补丁版本 +0.0.1** | `x.y.z` → `x.y.z+1` | `0.1.0` → `0.1.1` |
| **有功能更新** —— 新增了使用者可感知的新能力（新工具 / 新判定方法 / 新文档章节），或现有能力的行为变了 | **次版本 +0.1.0**，补丁归零 | `x.y.z` → `x.y+1.0` | `0.1.0` → `0.2.0` |
| **破坏性变更** —— 现有用法不再成立（工具的入参 / 输出格式变了、目录结构变了、判定口径换了） | **次版本 +0.1.0**，并在 [CHANGELOG.md](../CHANGELOG.md) 的版本段落里**显式标注** | `x.y.z` → `x.y+1.0` | `0.1.0` → `0.2.0` |

进位是**连锁**的：次版本进位时补丁必然归零（`0.1.0` 的下一次功能更新是 `0.2.0`，
不是 `0.2.1` 也不是 `0.1.2`）。

## 2. 怎么判断「有没有功能更新」

判断口诀：**打开 [TOOLS.md](TOOLS.md) 的工具表与 [docs/README.md](README.md) 的文档索引找答案 ——**

- 使用者能在工具表里**找到一个以前没有的工具**（新脚本），或者某个现有工具
  **跑一遍结果不一样了**（入参 / 输出格式 / 行为变了），或者索引里**多了一篇新的正本**
  → 有功能更新 → `+0.1.0`；
- 工具表与索引翻遍也找不到任何新东西，改的是「判得对不对」（结论 / 判据修正）与
  「说得好不好」（措辞 / 结构 / 补证据）→ 没有功能更新 → `+0.0.1`。

边界情况：

| 情况 | 算不算功能更新 | 理由 |
|---|---|---|
| 修一个「判据本该生效却没生效」的 bug | ❌ `+0.0.1` | 结论回到了它本来该有的样子，不是新结论 |
| 删掉某项能力 / 某个工具 / 某篇文档 | ✅ `+0.1.0` | 能力清单变了，使用者可感知的减法也是更新 |
| 新增 / 删除一个文档分区、给文档改名 | ✅ `+0.1.0` | 索引的结构变了 |
| 破坏现有用法（入参 / 输出格式变了、判定口径换了） | ✅ `+0.1.0` + CHANGELOG 显式标注 | 见 §1 第三行 |
| 只改文档、只改措辞、只动 CI 配置 | ❌ 连补丁版本都不给 | 见 §5：这类改动**根本不动版本号** |

拿不准时问一句：**写这一版的 Release 说明时，会不会出现「新增 / 变更 / 移除了某能力」
这样的句子？** 会 → `+0.1.0`；全文只有「修复 / 调整 / 优化」→ `+0.0.1`。

> 本仓的「能力清单」就是 [TOOLS.md](TOOLS.md) 的工具表：
> **工具表多一行 / 文档表多一行** → `+0.1.0`；
> 只是某篇文档里的一段结论被修正（例如 [LNA-FAKE-IP.md](LNA-FAKE-IP.md) 的判据收紧）→ `+0.0.1`。

## 3. 版本号在哪维护

**只有一处：[CHANGELOG.md](../CHANGELOG.md) 的版本标题**（形如 `## [0.1.0] — 2026-10-20`）。

本仓**没有构建产物版本号**，因此：

- 版本号**不从任何构建产物里读**，也没有第二个「真正的版本号」藏在别处 ——
  改版本号 = 改 [CHANGELOG.md](../CHANGELOG.md) 的段标题；
- 由它派生出两处**必须与标题一致**的引用：
  - Release 说明文件名 [docs/release-notes/0.1.0.md](release-notes/0.1.0.md)
    （格式正本见 [docs/release-notes/README.md](release-notes/README.md)）——
    **文件名不带 `v`**；
  - 发版 tag（`v0.1.0` 形式，`v` 前缀只属于 tag，与文件名区分）。

> 别去 `tools/` 下的脚本里找版本号 —— 三个脚本都没有版本字段；
> 本仓也**没有** `package.json`，**不要**为了「放个版本号」去新建一个。

## 5. 不发版的时候：不要动版本号

**不发版就不要动版本号** —— 只改文档、只修拼写、只动 CI 配置、只补证据，一律不动。

这类改动只在 [CHANGELOG.md](../CHANGELOG.md) 顶部的 `## [未发布]` 段**追加一条**，
**不新开版本段落**。理由：版本号是给使用者看的「这次拿到了什么」的标记，
文档措辞、流水线与证据的修正不改变使用者拿到的东西 —— 提前动号等于把下一个版本号吃掉。

`[未发布]` 段攒够了再发版：把段标题改成 `## [x.y.z] — <发版日期>`，
并补一份同名的 Release 说明。

## 6. 与 CHANGELOG 的关系

| 主题 | 唯一正本 | 其余位置怎么写 |
|---|---|---|
| **版本号本身**（当前是哪个版本、历史上有哪些版本） | [CHANGELOG.md](../CHANGELOG.md) 的版本标题 | 只留一句话 + 链接，不复制版本历史 |
| **进位规则**（下一次该动哪一位） | 本篇 §1 与 §2 | 只留一句话 + 链接，不抄表格全文 |

两处都写全文，迟早各改各的 —— 单一正本原则见 [docs/DOC-RULES.md](DOC-RULES.md)。
