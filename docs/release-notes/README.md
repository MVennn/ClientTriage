# release-notes/

> **一句话**：这里放**面向使用者**的 Release 说明，文件名 = `versionName`；
> 格式规则只在本篇定义一次。

放**面向使用者的** Release 说明，文件名 = `versionName`（**不带 `v`**）：

```
docs/release-notes/0.1.0.md
```

**文件名不带 `v`** —— `v` 前缀只属于发版 tag（`v0.1.0`）；
Release 说明文件名就是版本号本身（`0.1.0.md`）。

版本号规则见 [VERSIONING.md](../VERSIONING.md) §1–§2（唯一正本）；
版本号本身在根 [CHANGELOG.md](../../CHANGELOG.md) 的版本标题里维护。

## 为什么要单独放一份

`CHANGELOG.md` 是**开发者记录**：拆仓动作、结论修正、欠账清单、待验证项。
Release 说明是**给使用者看的**，要短、写成清单、只讲「这一版现在有什么、能干什么」。
两者受众不同，不能一份两用。

## 形状

**清单，不是文章。** 开头一句加粗说清这版是什么；紧接一行**反馈入口**（不是清单条目），
然后才是 `## 本版内容`，下按分区一行一条，最后是固定尾巴。

```markdown
**本仓首次独立成仓：PC 侧经代理访问境外服务的排障方法与工具，含 Chrome 地区种子清理、
Gemini 复测与 CDP 抓控制台。**

遇到问题、想要新功能，到 [Issues](https://github.com/MVennn/ClientTriage/issues/new/choose) 反馈 —— 请附上 Chrome / Windows 版本、执行的命令与输出原文。

## 本版内容

**工具**

- 新增 清地区种子 —— 工具 → 地区种子；完全退出 Chrome 后清掉 5 个 `variations_*_country` 键，写前留备份。
- 新增 Gemini 复测 —— 工具 → Gemini 复测；切 WiFi、起临时 Chrome、抓控制台、截图、清理、切回热点。
- 新增 抓控制台 —— 工具 → CDP 抓控制台；把「页面只剩输入框」变成一条明确的控制台错误。

**文档**

- 新增 LNA 与 fake-IP 机制 —— 文档 → 机制；Chrome 155 的 LNA 与 mihomo fake-IP 的冲突、证据与解法。

---

> 风险提示：本仓只做客户端侧的定位与取证，不提供任何绕过服务方地区限制的方案；
> 修改浏览器配置前请自行备份。使用本工具产生的任何后果由使用者自行承担。
> 完整声明见 [README 免责声明](../../README.md#免责声明)。
```

结尾那几行风险提示段是**固定尾巴**，每版照抄不动。它**不算重复内容**。

## 反馈入口：写在开头，链接必须是绝对地址

同一份正文可能被发到源码仓库以外的地方，入口链接只能写**绝对地址**
`https://github.com/MVennn/ClientTriage/issues/new/choose`：相对链接在别的页面会落到
错误的 Issue 列表；`issues/new/choose` 会先让用户选「问题反馈（Bug）」还是「功能建议」。

**反馈入口是一行正文，不是清单条目**，位置在加粗总结之后、`## 本版内容` 之前。
已发布的历史正文不回填；新写的版本按这个形状来。

## 一条怎么写

```
新增 / 调整 / 修复 / 优化 + 对象 —— 入口或触发方式；一句话它现在能干什么
```

- **动词只有四个**：新增（以前没有）、调整（行为、默认值、位置变了）、
  修复（以前不对，**含底层与实现层**）、优化（使用者能感知的更快 / 更省事 / 更准）；
  另有「移除」用于删工具或删文档。都写全称 —— 单字「修」读着不像词。
- **对象名照抄实际名字**：工具用脚本名（`tools/clear-chrome-region.js`），
  文档用文件名（`docs/LNA-FAKE-IP.md`），现象用**使用者会搜的那个词**
  （「Gemini 页面只剩输入框」，不是「islands bundle 加载失败」）。
- **入口**写使用者点得到的位置：「工具 → 地区种子」「文档 → 机制」；
  不需要找入口的（现象本身就是入口），直接写场景。
- **功能**一句说完，写使用者拿到什么。不写怎么用、不写为什么。
- 说人话。`net_error = -385`、`fake-IP 段`、`initiator` 这类只对开发者有意义的词别写；
  真要交代限制，写使用者看得见的后果（「Google 商城里装扩展会报 Image decode failed」）。
- 一行一条。两句才说得清 → 拆成两条，或者这条本来就该留在 CHANGELOG。

## 底层与内部改动：算「修复」，而且要拆开写

这条是给「使用者看不出区别、但代码确实改了」的改动定的。**它们也算本版内容，
必须写；而且要一条一条拆开，不许打包成一句。**

| 改了什么 | 动词 | 一行怎么写 |
|---|---|---|
| 底层缺陷（竞态、覆盖、误判、判据错） | 修复 | 写「以前会怎样」的后果，不写根因 |
| 重构 / 拆文件 / 收敛路径（行为零变更） | 修复 | `修复 代码拆分 —— 哪几处拆开，行为零变更` |
| 删死代码、删悬空注释 | 修复 | `修复 死代码 —— 删了哪几处，行为零变更` |
| 文档口径纠错 | 修复 | 写纠了什么口径，不写讨论过程 |
| 仓库结构（文档正本新增、目录调整） | 调整 | `调整 仓库 —— …`；使用者不可见的也照写 |
| 使用者能感知的更快 / 更省事 / 更准 | 优化 | 写「快在哪」，能给数字就给数字 |

**禁止写法**：

- ❌ `优化 代码整理 —— 大文件按职责拆分、包依赖方向收敛，行为零变更`
  —— 三个改动压成一句，对不上 CHANGELOG，下个版本没人知道拆了哪些文件；
- ❌ `优化 稳定性 —— 中危 3 条、低危 10 条全部清零，细目见 CHANGELOG`
  —— 「细目见 CHANGELOG」等于没写，使用者和我们自己都不会去翻；
- ✅ 拆成 4~6 行，每行一个对象，行尾该标「行为零变更」的就标。

一句话记法：**凡是在 `git diff` 里出现过的东西，说明里都要有一行**。
写不长不是本事，漏了才是问题 —— 篇幅红线排在覆盖率之后。

## 覆盖率红线

**凡本版改过的东西，必须全部出现在 Release 说明里**，动词四选一（新增 / 调整 / 修复 / 优化），
一行一条。没有例外：

- 结论修正（根因变了、修法变了）→ 并进「修复」分组，一行写「以前会怎样」+「现在怎样」
- 新增 / 改写文档 → 并进「文档」分组，照写
- 纯重构（行为零变更）→ 并进「修复」分组，**按对象拆成多行**
- 工具副作用变了 → **必须写**，并同步改 [PITFALLS.md](../PITFALLS.md)（踩坑正本）

写完拿 CHANGELOG 对应段落逐条对：**CHANGELOG 里的每一处使用者可感知的改动，
Release 说明里都得能找到对应行**。叙事留在 CHANGELOG，说明只要一行短句。

### 篇幅

- 覆盖率红线优先于篇幅：先保证**一条不漏**，再谈合并。
- 分组按「工具 / 文档 / 结论」走，不按轻重排。
- 合并手法：同一主题的多处小改并成一行（但要列出对象）；审查修复写使用者可见的后果，
  不写根因长文。

## 别写这些

| 别写 | 为什么 |
|---|---|
| 第二人称叙述（「点一下就…」「你可以在…里改」） | 使用者要的是有什么，不是操作步骤；步骤归 README |
| 「原来是这样，所以现在…」的原因与取舍 | 解释属于 CHANGELOG |
| 实现原理、抓包原文、字段名 | 同上 |
| 开关默认开还是关、改完要不要重启 | 通用信息，不随版本变 |
| 「之前是什么样」的对比 | 只有修复条目允许一句症状（「装扩展报 Image decode failed」），其余不写 |
| 「本版没有破坏性变更，直接覆盖安装」 | 没变更就不用声明；**有**的时候才必须写 |
| 凑数的「注意」区块 | 见下 |

## 「注意」区块：能不写就不写

只在**使用者不知道就会出问题**时才写，最多一两条：

- ✅ **有破坏性变更** —— 工具的入参 / 输出格式变了、目录结构变了、命令不再兼容。**必须写**。
- ✅ **已知的、会被当成新 bug 的问题** —— 例如某条判据在某环境下不成立。如实写一条，
  免得被重复报。
- ❌ 每版都一样的操作提醒、性能说明 —— 不写。风险提示**例外**：
  每版说明末尾固定附风险提示段，属固定尾巴，不算重复内容。

## 改已经发出去的说明

版本发布后要改文案，改 `docs/release-notes/<版本>.md` 再走一次发布流程覆盖即可。
**不要**直接改已经对外的说明内容而不 bump 版本 —— 那会让 CHANGELOG 与说明对不上。

写完 `docs/release-notes/<版本>.md`、在根 `CHANGELOG.md` 顶部补该版本段落、
打一个同名的 tag（`vX.Y.Z`），发布流程就会用它当 Release 说明；
找不到对应文件时退回 CHANGELOG 的对应段落（并在日志里 `::warning::` ——
那段是写给开发者的，使用者看到的是噪音）。
